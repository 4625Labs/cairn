# E7 Debug: `ask --approve` never shows a question

## Root cause (firmware, found by reproduction on the Mac; device not contacted)
ESP32-S3 HWCDC `Serial` has a **256-byte RX queue** unless `Serial.setRxBufferSize()` is called before `Serial.begin()`
(core 3.3.10 HWCDC.cpp: "RX Buffer default has 256 bytes if not preset"). On an ask the hub sends one burst:
agents.begin(28 B) + agent(90) + agents.end(36) + question(158) = **312 bytes**. The first 256 B arrive (3 whole frames,
so rx_frames +3), the tail of the question frame is dropped by the queue, and the first 102 B of it (256 - 154) sit in the
decoder until the next hub frame breaks the CRC and they are discarded: bad_frames +102. Exactly the observed "+3 / +102".

Not the hub, not the JSON shape: I captured the real bytes (hub.mjs attachDevice + a hello/question over the adapter socket)
and fed them to the firmware `dial::Decoder` (dial_frame.h, c++ -std=c++11):

    full 312 B:  frame len=20 agents.begin / len=82 agent / len=28 agents.end / len=150 question
                 fed 312 of 312: frames=4 discarded=0 corrupt=0
    first 256 B: 3 frames (begin, agent, end)   fed 256 of 312: frames=3 discarded=0 corrupt=0   (question missing)

The question JSON `{t,id,requestId,questions:[{key,q,multi,options}]}` matches parseQuestion/onHostMessage field names and types
(requestId key-like, questions 1..4, key, q, optional bool multi, options 1..6). Frame cap 2039 vs hub 2000-byte JSON cap is fine.
Any question larger than 256 B (up to ~2 KB allowed) could never have worked.

## Fix (firmware, 3 lines)
agent_dial.ino setup(): `Serial.setRxBufferSize(4096);` before `Serial.begin(115200);`. I did not touch the TX queue
(setTxBufferSize before begin() runs with tx_lock NULL: untested risk). Caveat UNVERIFIED: device->host frames over 256 B
(diag.state ~270 B) go through a 256 B TX ring with timeout 0; they worked in the evidence, left alone.
Hub change: none, hub-side pacing cannot fix a 2 KB frame into a 256 B queue.

## Regression test
`target/agent-dial/tests/check_rx_buffer.py`: asserts setRxBufferSize precedes Serial.begin and is >= 4086, that the hub's ask burst
(312 B) exceeds the default 256 B queue, and that it decodes 4/4 frames. Output: `PASS: burst 312 B > 256 B default queue; RX queue set to 4096 before Serial.begin; 4/4 frames decode`
(Add to tests/run.sh if desired; I did not edit it.)
