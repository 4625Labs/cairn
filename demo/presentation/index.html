Cairn

Lessons that outlast the bug.

A stack of stones marks the trail so the next traveler does not repeat the last one's mistake.

Hello, we are Cairn. One sentence: Cairn turns each security mistake into a lasting plain-English lesson, checks everywhere else that mistake hides, lets an AI agent propose the fix without holding your keys, checks the agent's work independently, and makes a person approve it on a physical device. The name: a cairn is a stack of stones that marks a trail. Timing: this deck is about 5 minutes plus Q and A. Keys: arrows or space to move, n for notes, p for all slides, f for fullscreen.

The problem

We fix a bug once. The same mistake comes back.

Unvalidated input

Text or numbers from outside a program are used as if they were well formed.

Risky dependencies

Versions pinned to "*" or loose ranges that change under you.

AI agents write code

They now write much of it, and they can repeat a bad pattern at speed.

Nothing remembers which classes of mistake have already bitten the team, where else they hide, or whether a fix held.

Plain English. Teams fix a bug one instance at a time, so the class of mistake returns. Two classes hurt the most in our own repos: unvalidated input and risky dependencies. AI coding agents now write much of the code, and if they learned a bad pattern they repeat it quickly. Nobody and nothing keeps the memory. That is the gap. Our test material is real: the public esptember project, with a real seed bug where a Wi-Fi network name is pasted into a web page without escaping.

The idea

The permanent asset is a plain-English card, not a regex.

Behavior card (a file)

"Text or numbers that arrive from outside the program are used as if they were well formed: not checked for type, length, range or characters."

Versioned, human-readable, and independent of any scanner. We wrote two: unvalidated-network-input and unpinned-dependency.

One loop, run again every time:

Learn→Sweep→Fix→Guard→Remember

Every slot in the loop is swappable. The cards are what survives.

The key idea: the card is the lesson. It describes behavior in plain English, so it outlives any one scanner. The loop: Learn the lesson from one bug, Sweep for cousins of it, Fix with an agent, Guard so it cannot quietly return, Remember every step as a row. Honest note: Pi has no public API, so our cards are just files and we claim no Pi integration.

Architecture

Swappable slots, each doing a real job.

Six slots. Detect: Semgrep, with rules we wrote, finds the seed and its cousins and re-scans patches. Cards: plain files, the permanent asset. Record: ClickHouse keeps an append-only event table and a versioned cards table, and answers the incident and spread questions. Act: a Guild-hosted fixer agent opens a pull request while holding no GitHub token. Isolate: Akash runs the scanner and the dashboard on rented machines. Approve: the human gate, a physical button on the M5Stack Stopwatch, with a terminal prompt as a fallback. Any slot can be swapped without losing the cards.

Demo beat 2: remember it in ClickHouse

Every action is a row. One query answers "is it spreading?"

cairn_events

Append-only. Kinds: finding, cousin_candidate, human_confirm, agent_write, agent_ignored_finding, pr_gate, device_approval, reintroduced.

cairn_cards

Versioned. A new version is stored only if the card file's hash changed. First sync inserted 2 cards (v1 each); the second inserted 0.

Queries: incident (same card, several events in a window, several files: one problem?) and spread (new files since the last look). The Cairn Board dashboard shows them.

Honest: append-only is by convention in code (SQLite copy has triggers); real enforcement needs INSERT/SELECT-only grants. The incident query was shown on labelled demo data, not run on live data.

Every finding, agent action, ignored warning and approval is an append-only row. The point is the question, not the dashboard: is this one problem and is it spreading. The append and spread queries ran live on ClickHouse Cloud. The incident query was only run on the synthetic demo dataset, which is labelled DEMO. The cards table is versioned so you can see how a lesson evolves. Counts in the live table include mixed real and synthetic rows, so we quote none.

The twist

The agent fixed the bug and also corrupted unrelated lines.

ESP_ERROR_CHECK  -> eSP_ERROR_CHECK
nvs_erase_all    -> nvo_erase_all
</select>        -> </celect>
httpd_start      -> httpd\x1fstart

Semgrep Guardian scanned the written file (1 scan, 4 findings in a test file) but it runs after the write and cannot block it. The agent kept the lines. We logged it as agent_ignored_finding.

Cairn's independent gate

Patch hygiene check on PR #1:

9out-of-scope lines
6identifier typos

GATE: BLOCK Nothing reaches a person unless the independent re-scan, test and hygiene check are clean.

The real story. The agent fixed the bug, but while retyping the file it also mangled lines that had nothing to do with the fix: ESP_ERROR_CHECK became eSP_ERROR_CHECK, nvs_erase_all became nvo_erase_all, the closing select tag became celect, and httpd_start got a hidden 0x1F byte. That file would not compile. The Semgrep Guardian hook did run on a separate test file and reported 4 findings, but it runs after the write and cannot stop it, and the agent kept the code. So Cairn adds its own gate: a scope allowlist per card plus an identifier typo check. On PR 1 it names 9 out-of-scope lines and 6 suspected typos, gate line says BLOCK with unrelated_changes 15. Also: the agent's helper has a real truncated-entity bug that our unit test caught. Limits: additions are not scoped, short identifiers are ignored.

Demo beat 4: a person approves on a physical device

The M5Stack Stopwatch running Agent Dial.

Bug found on the real device: the question never appeared. The hub's burst was 312 bytes; the ESP32-S3 USB serial receive queue holds 256 by default, so the question frame was cut off.

Fix: one call, Serial.setRxBufferSize(4096), before Serial.begin.

Real round trip: the gate passed, the dial answered Allow, rows landed in ClickHouse.

When the checks are clean, the request goes to the one place a person cannot be bypassed: a button on a wrist-sized device. Left button moves focus left, right button moves right, both together select. We generated the dial firmware and the host hub from the Day 35 spec of the public esptember project. First on-device attempt: the question never showed. Root cause by reproduction: the hub sends 312 bytes at once, the chip's USB receive queue holds 256, so the tail of the question frame was dropped. The fix is a single added call before Serial.begin. Real end-to-end result: gate pass, real dial answered Allow, pr_gate and device_approval rows in ClickHouse. Tests: 190 frame vectors, 133 host-bridge checks, 40,183 reference model checks, 17 simulated round-trip checks. If the device misbehaves, there is a simulated dial; say plainly that it is simulated. Pressing Deny writes nothing.

  • Gate that blocked the agent's work
  • Real device approval: Allow

Not claimed

  • Incident query: demo data only

Be direct. Pi has no public API, so cards are plain files and we claim no Pi integration. Semgrep matches code shape and some results are noise; also the default Guardian ruleset did not flag our planted bug, which is exactly why we wrote our own rules. The dial firmware is a minimal viable product: no LVGL graphics, no voice, no Wi-Fi. The incident query ran on labelled demo data. The hygiene gate is a regex allowlist per card with known limits. Anything not on the real side was not done.

What is next

Point Cairn at your company's private repos.

  • The first two cards, unvalidated input and risky dependencies, are the starting library.
  • Every incident adds a card; every card is checked on every repo, forever.
  • The library compounds, whichever scanner, agent host or device sits in the slots.
Next step is simple: aim it at private repositories, where these two classes of mistake hurt most. Each new incident becomes a card, and each card is checked everywhere. Because the slots are swappable, the cards keep their value even if a tool changes. Not yet done: broader gate rules and dataflow-aware detection.
